# MCP 服务设计文档

## 1. 定位与拓扑

工具服务：agent 通过 MCP 协议调用它提供的工具。

```text
飞书用户 → 飞书机器人 → agent → [MCP 服务] → 工具 → 上游/数据库/…
```

对 MCP 来说，**调用方只有一个：agent**。会话（`session_id`）和会话类型（`chat_type`）
由 agent 在每次调用里带上，用来做归因和公平性。

**不做的事**（都是有意为之，理由见 §11）：不保存业务状态、不排队、不自动重试、不自己
签发身份（OAuth）。

## 3. 鉴权

### 3.1 模型

一张 `名字 → token` 表，一个调用方一行：

```bash
MCP_AUTH_TOKENS="feishu-agent:<token>,ops-agent:<token>"
```

- **名字不参与校验**，只用于日志、审计归因和限流分桶。
- **允许重名**——轮换时同一个 agent 的新旧 token 会短暂并存。
- 旧式的单个 `MCP_AUTH_TOKEN` 仍可用，自动归到名字 `default`。
- **两个变量同时设 → 拒绝启动**：那几乎总是"迁移到一半忘了删旧的"，表现是旧 token
  还在悄悄放行。

`caller_name()` 从**已验证的 token** 反查名字，是全链路唯一不可伪造的身份。

### 3.2 中间件顺序

```text
BearerTokenMiddleware          （ASGI 层，只对 HTTP 生效）
  └ AuthContextMiddleware      （SDK 的：把 scope["user"] 放进 contextvar）
      └ MCPServer
          └ SessionContext     （MCP 中间件层，HTTP/stdio 都过）
              └ AuditLog
                  └ RateLimit
                      └ ToolTimeout
                          └ 工具
```

两层"中间件"不是一个东西：`BearerTokenMiddleware` 包 HTTP 请求，`ServerMiddleware`
包 MCP 请求。鉴权失败在 HTTP 层就返回 401，**不会进入 MCP 中间件链**——所以审计日志
里看不到被 401 挡掉的请求（只有 `auth.py` 的一条 WARNING）。

### 3.3 401 的形状

```text
HTTP/1.1 401 Unauthorized
content-type: application/json; charset=utf-8
www-authenticate: Bearer realm="mcp"

{"jsonrpc":"2.0","id":null,
 "error":{"code":-32600,"message":"未授权：缺少或错误的 Bearer token（…）"}}
```

两个细节都是实测倒推出来的：

- **响应体必须是 JSON-RPC 错误对象。** SDK 客户端拿到 4xx 时会按 JSON-RPC 解析响应体，
  解析成功就把 `message` 交给调用方；失败则退化成一句 `Server returned an error response`
  （实测甚至只抛一个空消息的 `ReadError`）。SDK 自己的鉴权中间件用的是 RFC 6750 那套
  `{"error": "invalid_token"}`，正好落进后一种。
- **不能加 `Connection: close`。** 连接何时关闭是 uvicorn 的事；应用自己在响应头里声明
  关闭，会让它在客户端读完响应前就关掉 socket，实测约 1/10 的请求变成
  `ReadError: Connection reset by peer`。

比较用 `secrets.compare_digest`，不用 `==`：字符串比较在第一个不同字符处返回，耗时差异
可被用来逐字节试探。

### 3.4 轮换（零停机）

```bash
# 1. 加上新的，旧的一起留着（重名允许）
MCP_AUTH_TOKENS="feishu-agent:新,feishu-agent:旧"
# 2. 重启：新旧都有效
# 3. 各调用方陆续切到新 token
# 4. 去掉旧的那行，再重启
```

吊销 = 删掉那一行。只影响一个调用方。

## 4. 限流

### 4.1 三档额度

| 档 | 环境变量 | 桶的键 | 默认 |
|---|---|---|---|
| 单聊会话 | `MCP_SESSION_RATE_LIMIT_PER_MINUTE` | `session_id` | 0 = 不限 |
| 群聊会话 | `MCP_GROUP_RATE_LIMIT_PER_MINUTE` | `session_id` | 0 = 不限（跟随上档） |
| 调用方（总闸） | `MCP_RATE_LIMIT_PER_MINUTE` | 已验证的调用方名字 | 0 = 不限 |

只算 `tools/call`；`initialize`、`tools/list` 不吃额度。

**这个额度的性质是一条"标准线"，不是硬天花板。** MCP 自身的容量可以靠加机器资源升级，
所以它不是需要死守的约束；它存在的意义是给调用速度一个统一、可预期的基准（以及挡住明显
跑飞的循环）。真正的硬约束在上游——见 §4.7。

### 4.2 算法：令牌桶

- 每个桶：**容量 = 一分钟的量**，**按秒连续补充**（`per_minute / 60`）。
- 因此允许"攒满一分钟的额度一次打出去"：安静时桶是满的，突发可以瞬间用完；之后只能
  按补充速度来。**长期平均被压在额度上，短期突发不误伤。**
- **攒有上限**：容量就是一分钟的量，安静一小时也只有这么多，不是线性累积。
- 和固定窗口相比没有边界效应（窗口计数在整点前后可以放行两倍）。

`take()` 里**没有 `await`**：单线程事件循环中不会被切走，"读-改-写"不会交错，**因此
不需要锁**。给它加任何 `await` 都会把这里变成竞态。

### 4.3 检查顺序与原子性

从细到粗：会话（群聊/单聊）→ 调用方。

先查细的：**细的超了就不该再扣粗的令牌**，否则一个会话刷爆自己额度的同时会把总闸也吃光。
（有测试钉住：`test_session_rejection_does_not_eat_the_caller_quota`。）

### 4.4 缺标签 → 拒绝

| 情况 | 码 | 说明 |
|---|---|---|
| 触发额度 | `-32000` | `这个群聊调用过于频繁：oc_xxx 每分钟最多 50 次` |
| 配了额度但缺标签 | `-32602` | 消息里列出合法取值 |

用 `-32602`（invalid params）而不是限流码：**这是调用少给了东西，不是调得太频繁**。
跳过不检查等于留洞——不带标签的跑飞循环完全不受这一层管，而那正是它要防的。

### 4.5 群聊额度回落

群聊和单聊在数据上都是一个会话，但群聊的额度是**全群共享**的（一个人能把额度用光）。
所以群聊有自己的数；**不配就跟随单聊额度**——否则只写"每会话 20"会让群聊变成不限，
"少配一个变量把口子开大"是最容易忽略的配置事故。

### 4.6 已知边界

- 桶表在**进程内**，重启清零；多副本各算各的（§12.4）。
- 桶表**只保留活跃会话**：每 60 秒扫一次，攒满的桶直接删掉。满桶和不存在是等价的，删它
  不改变任何行为；而删没满的桶等于把剩余额度抹掉重来，是限流绕过。没有这一步的话，这张
  表会随出现过的所有会话一直涨。
- `session_id` / `chat_type` 是自称的，**换个值就是新桶**。只有调用方那档不可伪造。
- 超限是**快速失败**，不是排队（§11）。
- 限流管"多快"，不管"同时几个"——后者由 agent 侧按会话串行化解决。

### 4.7 上游额度（飞书 API）：现在的取舍与将来的做法

**现状：只有一个 MCP 额度，没有针对上游额度的专门控制。** 这是有意的——工具的接口还少，
一个全局数字就够用；而且 MCP 自身容量可以靠加机器升级，不是需要死守的约束。

但要知道这个简化在哪里不成立：

1. **飞书额度是按应用全局共享的。** 不管多少个会话，消耗的是同一个配额。所以和它对得上的
   是**总量那档**（`MCP_RATE_LIMIT_PER_MINUTE`），单会话那档只解决公平。
2. **一个全局限流是上游额度的粗代理。** 不同飞书接口的额度可能不同，一个数字只能取最保守
   的那个——对便宜接口过度限制，对贵的接口保护不足。
3. **MCP 不是上游额度的唯一消费者。** 机器人自己发消息、别的服务也可能用同一个 app，所以
   MCP 侧最多保护一部分。

将来真要管住上游额度，顺序应该是：

| 步骤 | 在哪做 | 说明 |
|---|---|---|
| ① 工具内对上游限流 | **工具里**，不是框架模块 | 它知道具体接口的额度；框架不知道 |
| ② 处理上游 429 | **工具里** | 转成明确的 `ToolError`（"上游限流，稍后重试"），和 MCP 自己的 `rate_limited` 区分开——一个是"等一会儿"，一个是"调用方太快" |
| ③ per-tool 配额 | 框架 | 桶的键加上工具名。只有工具确实打多个额度不同的接口时才值得 |

②里的区分很重要：如果上游 429 被报成 `rate_limited`，调用方会按 MCP 的额度退避，而实际
该等的是上游——等多久、等哪个，完全错位。上游失败应该走 `ToolError`（工具语义），MCP 的
限流错误才走 `-32000`（协议语义）。

## 5. 审计

每次 `tools/call` 一条：

```text
调用完成：feishu-agent[oc_xxx/p2p] → search（0.31s，参数：limit、query）
调用出错：feishu-agent[oc_xyz/group] → fetch（1.02s，参数：id）
调用失败：feishu-agent[无会话/无类型] → slow（0.50s，参数：seconds）：工具 slow 超过…，已放弃等待
```

- `调用出错` = 工具用 `ToolError` 报的失败（**正常返回值**，`isError=true`）。
- `调用失败` = 抛出来的异常（限流、超时、崩溃）。
- **只记参数名，不记参数值**：值是调用方的数据（飞书那边就是用户原文），日志通常比
  数据库活得久、管得松。
- **只记 `tools/call`**：建会话时的 `initialize` / `tools/list` 会把真正的调用淹掉。
- 位置在链的最外层，被限流挡掉、被超时放弃的调用也要留记录。
- 每次成功返回的 `CallToolResult._meta` 里还带 `execution_time_ms`（服务端耗时，
  毫秒）。它和 `serverInfo` 合并，**不在正文里**，模型看不到；调用方可以读它做
  日志和指标。换算函数是 `timing.execution_time_meta`。

## 6. 超时

`MCP_TOOL_TIMEOUT_SECONDS`（默认 30，0 = 不限）。

```text
工具 slow 超过 0.5 秒没有返回，已放弃等待（它可能仍在执行，重试前请确认这个工具是否幂等）
```

- **超时只是"不再等它"，不是"中止它"**：同步工具在工作线程里跑，Python 杀不掉线程；
  异步工具停在下一个 `await` 点，已经在飞的写入不会收回。所以这个值按"最慢的正常调用"
  定，别当中断手段。
- 消息里明说"可能仍在执行"：超时是**最不确定**的失败，调用方最自然的反应（重发）恰是
  最危险的。
- 工具自己抛的 `TimeoutError`（它调的上游超时了）**不会被误认**成工具超时——两个是同
  一异常类型，实现里查的是"超时窗口有没有真的到期"（`timeout.expired()`）。

## 7. 错误模型

### 三类失败

| 谁失败 | 怎么写 | 客户端看到 |
|---|---|---|
| 工具**预料到**的失败 | `raise ToolError("人话")` | `isError=true`，原文给模型 |
| 中间件拒绝（限流、超时、缺标签） | `raise MCPError(code, message)` | 协议错误，原文给调用方 |
| 工具**没预料到**的崩溃 | 让它抛 | 只有 `Error executing tool <名字>`，细节只进日志 |

**异常文本不会漏给客户端**——第二类崩溃的详情（token、SQL、内部主机名）只进服务端日志。

### 错误码

| 码 | 含义 | 来源 |
|---|---|---|
| `-32000` | 被限流 | 自定义（JSON-RPC 把 -32000..-32099 留给实现） |
| `-32001` | 工具超时 | 自定义 |
| `-32602` | 缺/认不出 `_meta` 标签 | 标准 invalid params |
| `-32700` / `-32600` / `-32601` / `-32603` | 解析 / 请求非法 / 方法不存在 / 内部错误 | 标准 |

### 结构化失败信息（`error.data`）

`message` 是给**人和模型**看的；`data` 是给**调用方代码**看的。**重试决策靠 `data`，
不靠解析消息**——措辞随时会改，中文更不该被程序当协议。

| `kind` | 附加字段 | 含义 | 该重试吗 |
|---|---|---|---|
| `unauthorized` | — | token 不对 | 不重试，去修配置 |
| `rate_limited` | `scope`（`session` / `group` / `caller`）、`limit_per_minute` | 超额度 | 不立即重试；按额度退避 |
| `timeout` | `tool`、`timeout_seconds`、`may_still_be_running` | **不知道做没做** | **看幂等性**（§11.1） |
| `missing_meta` | `field`、`allowed`（该字段有取值域时） | 调用少给了东西 | 不重试，修调用 |
| 没有 `data` / 认不出 | — | 未知失败 | 默认不自动重试 |

输出是 `MCPError(code, message, data)`，客户端侧（参考实现 `agent_client.py`）把它归一成
`McpConnectionError.data`，所以 `except McpConnectionError as e: e.data["kind"]` 直接可读。

## 8. 会话标签

### 8.1 两个标签

| 标签 | `_meta` 键 | 取值 | 用途 |
|---|---|---|---|
| 会话 | `session_id` | 飞书会话 id | 归因、按会话限流 |
| 类型 | `chat_type` | `p2p` / `group`（与飞书一致） | 选择用哪套额度 |

**它们和 `caller_name()` 是两回事**：

| | 来源 | 能否用于判断 |
|---|---|---|
| `caller_name()` | 已验证的 token | 能——身份 |
| `session_id` / `chat_type` | 调用方在 `_meta` 里自称 | **不能**——只是标签 |

适合做归因和公平性，**不能**做权限判断。也不是 MCP 传输层的 `Mcp-Session-Id`（那是连接
级的，和"一次对话"无关）。

### 8.2 载体：`_meta`

```json
{"method": "tools/call",
 "params": {"name": "search", "arguments": {},
            "_meta": {"session_id": "oc_xxx", "chat_type": "group"}}}
```

`_meta` 是协议里的**开放**字段（保留键以 `io.modelcontextprotocol/` 开头），实测自定义
键会原样出现在服务端的 `ctx.meta` 里。

`chat_type` 只认飞书那两个取值；拼错、大小写不同、用别的词一律当没带（然后被限流层拒绝
并列出合法取值）——宽松地"猜一个"会让拼错变成静默的行为差异。

`SessionContext` 中间件把它们放进 contextvar，工具和其余中间件都能读
（`session.session_id()` / `session.chat_type()`）。

## 9. 工具注册与性质声明

- 每个工具模块暴露 `TOOLS` 元组；函数名即工具名，docstring 即描述。
- **重名拒绝启动**（SDK 默认只记 warning 然后让后者覆盖前者，被盖掉的工具很难查）。
- **不建模块级 server 单例**：注册只发生在 `register_all()` 里，所以工具能直接单测、同
  进程可多实例。
- 工具是普通 `async` 函数（同步函数也可以，SDK 会放工作线程）。

`@hints(...)` 声明工具性质，随 `tools/list` 下发（**模型也看得到**）：

```python
@hints(read_only=True)      # 只读
@hints(idempotent=True)     # 有副作用，但重复调用安全
@hints(destructive=True)    # 破坏性
```

**不声明 = 什么都不说**，调用方只能按"可能有副作用"对待。把有副作用的工具标成
`read_only` 是唯一会出事的错法。启动日志会把每个工具的性质打出来，"未声明"一眼可见。

> `@hints` 是**声明**，不是**执行约束**——它约束不了调用方，只提供判断依据。真正的
> 执行约束属于权限（§12.1）。

## 10. 配置与传输

### 10.1 配置

- 环境变量来自进程环境 + 工作目录的 `.env`（入口显式加载，**已存在的环境变量优先**）；
  启动时校验，配错直接起不来。
- 变量清单见 `.env.example`，说明见 README「配置」。

### 10.2 传输

Streamable HTTP，单端点（默认 `/mcp`），三种方法：POST（发消息）/ GET（服务端下行通道）/
DELETE（结束会话）。`json_response=True`：成功的响应是纯 JSON，不套 SSE。

取舍：关掉了"调用过程中回报进度/日志"的能力（那些消息本来搭在 POST 的 SSE 流上，实测在
JSON 模式下会被丢弃）。要写长任务、需要过程推送时，删掉这个参数即可，客户端不用改。

### 10.3 探活

`GET /healthz` → 版本号，不需要 token。**只证明进程活着**，不检查依赖（§12.6）。

## 11. 不应引入的模块（提醒）

以下三项在讨论中出现过，结论是**不要加**：

### 11.1 框架不做自动重试，但把判断依据交出去

**不加自动重试。** 重试对调用方不可见：一个已经超时的调用在后台又执行一遍，用户看到
"失败了"而消息实际发出两次——最难查的事故形态。

**但"不重试"不等于"什么都不给"。** 框架把判断所需的信息交出去，由 agent 代码和 LLM 各管
一半。

#### 分工

| 受众 | 拿什么 | 判断什么 |
|---|---|---|
| agent 代码 | `McpConnectionError.data`（§7） | 机械决策：等多久、修参数、连接失败重试 |
| LLM | 错误 `message` + 工具描述里的 `@hints` | 语义决策：超时了要不要再试、要不要先问用户 |
| 用户 | agent 转述的"状态不确定" | 需要确认时拍板 |

#### 判断表

| 失败 | 谁处理 | 动作 |
|---|---|---|
| `rate_limited` | agent 代码 | 按 `limit_per_minute` 估等待，有上限地退避重试 |
| 无 `data`（连接失败等） | agent 代码 | 有界重试 + 指数退避 |
| **`timeout`** | **LLM** | 查工具的 hints：只读/幂等 → 可有限次重试；否则 → 告诉用户"可能已执行"，让用户决定 |
| `unauthorized` | agent 代码 | 不重试，修 token |
| `missing_meta` | agent 代码 | 不重试，修调用（这是 bug） |
| 工具 `isError` | **LLM** | 读消息决定：换参数、换工具、还是回复用户 |

**核心规则**：能重试的前提是"知道这次确定没成功"。`kind=timeout` 明确表示"不知道"
（`may_still_be_running: true`）。

#### 让 LLM 判断的前提

`@hints` 只在 `tools/list` 的 annotations 里，**默认不会自动出现在 LLM 面前**。agent 必须
把它渲染进工具描述：

```text
search：在知识库里检索。[只读，可重复调用]
```

否则 LLM 拿不到幂等性信息——它只会看到一句超时，然后可能直接重发。

#### 重试预算

必须由 agent 设上限（次数 + 总时长），否则 LLM 可能进入重试循环，把一次失败放大成流量。

⚠️ `timeout` 是最危险的：重试时**前一次可能还在跑**（§6），并发会翻倍。

#### 什么时候结论会变

- **上游超时率高 + 操作幂等** → 工具内部加**有界重试 + 指数退避**是合理的。那是工具自己的
  事（它知道上游语义），不是框架模块。
- **要让非幂等操作也能安全重试** → 引入幂等键（`_meta.idempotency_key` + 服务端去重存储），
  而不是加重试循环。现在没做，因为没有"非幂等 + 有重试需求"的操作。

### 11.2 服务端排队 / 消息队列

**不加。** 限流是**拒绝**，队列是**延迟**：一个会话灌 1000 个任务进去，其他会话排在它
后面——队头阻塞，公平性反而更差。

排队应放在 **agent 侧、按会话**做（每个 session 一个队列/Lock），顺带解决群聊里"同一会话
多个请求交织、上下文互相污染"的语义问题——那是限流解决不了的。

**状态**：MCP 侧到此为止——决策已经定了（不做），准入控制已实现，没有剩余工作。排队与
串行化在 **agent 侧，未实现**（agent 本身也还没写）。也就是说：这个问题对 MCP 是终点，
对系统是交接点。

只有当出现**真长任务**（几十秒以上且调用方不需要立刻拿结果）、**跨重启不丢**、或**跨机器
扩展消费者**时才值得引入；且真长任务应先看 MCP 原生的任务模型（`tasks/*`），而不是外挂
一个 MQ。

### 11.3 用户级限流（`(会话, 用户)` 维度）

**不加。** 曾实现过，已删除。理由：机器人靠 **@** 触发，要吃掉一个群的额度得反复 @ 它，
行为可见且异常；场景中没有大规模提问。为理论问题增加一个维度，等于多一个旋钮、多一种
"配了但 agent 没传 `user_id` 就全挂"的故障模式。
